# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Enterprise AI governance middleware: intercepts every LLM prompt, runs it through a 9-stage governance pipeline, scores risk, enforces policy (ALLOW/WARN/REDACT/BLOCK), and forwards allowed prompts to Groq's LLM API. The core job is stopping confidential document content from reaching the LLM: uploaded documents are indexed into their constituent entities (regex identifiers + NER names), and every prompt is matched against that index. Everything that can block or redact is regex and dictionary lookups; the one model that runs per prompt (MiniLM, when sentence-transformers is installed) feeds an advisory similarity signal that can only warn. Full write-up of the pipeline, tech stack, and API surface is in [README.md](README.md) — read it for the architecture diagram and detection-category thresholds table.

This is a three-package repo: `backend/` (FastAPI + SQLAlchemy: auth, policy rules, anomaly detection, the LLM call, audit and analytics), `detection/` (a separate FastAPI service: everything that reads text — regex, the document index with NER, similarity, risk scoring, the answer check — and the protected documents), and `frontend/` (React/Vite dashboard). Each has its own `CLAUDE.md` with commands and architecture specific to that package — [backend/CLAUDE.md](backend/CLAUDE.md), [detection/CLAUDE.md](detection/CLAUDE.md) and [frontend/CLAUDE.md](frontend/CLAUDE.md) — loaded automatically when working in those directories. This root file only covers things that span them.

## Cross-cutting notes

- **Service boundary**: the backend never inspects text itself. `backend/app/services/detection_client.py` calls the detection service over HTTP for every prompt and every answer, and **fails closed** — if detection cannot answer, `DetectionUnavailable` becomes a 503 and nothing unchecked is sent to the LLM or returned. Keep it that way: never add a fallback that forwards a prompt when the check fails. The contract is the internal API in `detection/detection/main.py`; `backend/tests/test_seed.py` runs the real detection app in-process, so a change one side makes without the other fails there.
- **Testing**: `detection/tests/` covers leak detection, credentials, uploads, document indexing, the service API and (when the ML packages are installed) the real models; `backend/tests/` covers access control, admin-only routes, policy validation and migrations, seeding, failing closed and security defaults. No frontend test runner exists — `npm run build` (`tsc -b`) is the automated check on that side. CI (`.github/workflows/ci.yml`) is a single job, **Build and test**, run once per push (no separate pull_request run): lint + tests for both services (once on SQLite, once on Postgres), frontend build, then three Docker builds, a stack smoke test on Postgres (including a stopped-detection check) and real-model tests in the detection image. `main` is branch-protected: changes land only through a PR on which Build and test has passed — keep the job name in sync with the required check if it is ever renamed.
- **Docker**: `docker-compose.yml` at the repo root runs five containers — frontend (nginx), backend, detection, Postgres (a database per service; `postgres/init` creates detection's) and Redis — `docker compose up --build`. Postgres, Redis and detection are on an `internal` network with no route out and are not published; the backend is on both networks. The detection image pre-downloads the NER and embedding checkpoints in its build layer and runs with `HF_HUB_OFFLINE=1`; the backend image has no ML packages. See [detection/CLAUDE.md](detection/CLAUDE.md) for that layering and why torch is installed from the CPU-only index.
- **Accessibility**: all web UI code (`frontend/src`) must meet WCAG 2.1 AA. See [frontend/CLAUDE.md](frontend/CLAUDE.md) for specifics.
